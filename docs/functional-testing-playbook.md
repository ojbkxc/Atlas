# 功能测试作业手册（跨平台复用）

> 来源：2026-11 对某国内 SaaS 商城后台的两端功能测试（admin 管理后台 + seller 商家后台）——
> ① admin 四轮：159 页巡检 / 10 模块页面级 / S1–S18 完整业务流 / A1–A10 接口参数篡改与越权矩阵 / D1–D5 补测，交付 244 条缺陷；
> ② seller 商家后台两轮：83 页 / 7 个模块域 + 11 条跨模块复杂业务流（S5–S15），交付 89 条缺陷。
> 期间共产生 **29 条误报**（18 + 11，全部复核并留证），本手册把这些教训固化成**判据**。
>
> 用途：下次换平台时按本文走一遍流程。跨平台不变的判据已抽进**通用知识包**
> （`src/atlas/plugins/_common/knowledge/`，见 §16）；平台特有的选择器/坑点/契约放
> `plugins/<业务>/knowledge/`。**本文只讲跨平台不变的东西**。
>
> 配套：`docs/api-pitfalls.md`（接口失败现场判读）、通用/平台特有分工与分类台账见 §16 与
> `docs/element-ui-generic-knowledge.md`、私有知识目录 `ATLAS_KNOWLEDGE_DIR`（第一个用例的
> 平台特有沉淀放这里，**不进公开仓库**：真实域名、页面路径与业务缺陷属客户资产）。

---

## 0. 定位与适用边界

**适用**：无源码或弱源码访问权限的**黑盒功能测试**——被测系统是一个跑在远端、只有 UI 与 HTTP 接口的
业务系统，目标是找出功能性缺陷（而非性能/安全专项）。

**不适用**：单元测试、性能压测、需要构造复杂前置数据的深度集成测试。

**核心命题**：黑盒测试的产出质量，取决于**判据的严格程度**，而不是点击量。
四轮里最有价值的 15 条致命缺陷，全部来自「UI 上根本点不出来的路径」——

| 缺陷 | 为什么 UI 测不到 |
|---|---|
| 入库单 commit 无幂等 → 可循环刷库存 | UI 不会让你对「已完成」单据再点确认 |
| 已作废单可复活并二次入账 | UI 不暴露终态的逆向操作 |
| 同仓调拨被接受 | UI 下拉框结构性排除了同仓选项 |
| 退款金额超原单 | 审核动作不在后台，在 C 端 |
| 最小权限账号越权删等级 | 得有一把受限钥匙才试得出来 |
| 出库让总成本上涨 | 单点看每页都对，要跨三张表对账 |

**结论**：UI 点测是第一轮，必须配合**接口层篡改**与**跨模块对账**才够。

## 1. 三条不可谈判的判据纪律

这三条是全部误报的根因，写在最前面。

### 1.1 「没反应」类结论必须附请求实参

- **症状**：报「点 X 没反应」「筛选失效」「导出无反应」。
- **根因**：绝大多数是**探测姿势错**（选择器命中隐藏副本 / 点到下拉触发器 / 抓到导航项），
  不是系统缺陷。四轮 18 条误报里 **11 条**属这一类。
- **纪律**：任何「没反应」结论，必须给出
  ①**请求是否发出**（抓包）②**URL 参数变化** ③**响应 total/数据变化**。
  三项齐了才准写进缺陷表；给不出就按「未验证」处理，不得报。
- **实例**：`t-finance` 报「收款单高级搜索完全失效」，复核发现面板内隐藏/可见两组按钮、
  `first()` 命中了隐藏组；用可见按钮实测 `pay_status=PAY_YES` 使 total 43→23，筛选完全正常。
- **机器化落点（gap14）**：`atlas explore --auto` 的 assert 判据失败时，runs.jsonl 的失败步骤
  自动附**请求实参**（method/url/post_data，过净化刀）+ 响应快照 + 页面快照——「没反应类结论」
  在 AI 闭环里天然满足本条纪律；人写的缺陷表仍按本条手工取证。

### 1.2 校验判定看「有没有真的发出写请求」

- **症状**：争论「这个必填校验到底有没有生效」。
- **根因**：现代前端把校验做成 toast / 字段红字 / 静默阻断，**页面上看不出区别**。
- **纪律**：最可靠判据 = **有没有真的发出 POST/PUT/DELETE**。
  没发 = 前端拦下；发了且 200 = 后端接受。
- **延伸**：后端接受了不该接受的输入才是缺陷；「前端没拦但后端拦了」**不是缺陷**（属体验问题），
  单列不报。

### 1.3 否定性结论必须给方法 + 盲区

- **症状**：报「该模块无缺陷」「全部正常」。
- **根因**：黑盒测试的「没找到」可能是**没测到**，两者在报告里长得一样。
- **纪律**：每条否定性结论必须写清 ①用了什么手段 ②覆盖了什么口径 ③**已知盲区**。
  例：「越权矩阵 32 个端点正确返回 403」要补「导出类端点未全扫，且无第二账号可交叉验证」。
- **实例**：接口清单一次只爬到 92 个 GET、0 个写接口，若当时直接报「接口面已摸清」就是错的——
  实际写接口需要从建单页录请求才能发现。

## 2. 前端交互探测（Element UI 族）

Element UI 是本类后台的高频技术栈，其**组件渲染方式**是误报的最大来源。以下每条都在
`plugins/<业务>/knowledge/components.json` 有对应登记。

### 2.1 弹层内容挂 body，且存在隐藏副本

- **症状**：点弹层里的按钮没反应；或 `.first()` 拿到「看起来对」的元素但点不动。
- **根因**：`.el-popover` / `.el-select-dropdown` / `.el-dropdown-menu` 都 append 到 `body`，
  且**预渲染多份**（部分 `display:none`）。
- **处置**：一律加 `:visible` 过滤（或按 `getBoundingClientRect().width > 0` 过滤）；
  按钮在 `.el-form` **之外**，不能用 `.el-form button` 找。

### 2.2 下拉触发器 ≠ 动作按钮

- **症状**：点「导出」无下载、无请求、无提示。
- **根因**：按钮 class 带 `el-dropdown-selfdefine` 的是**触发器**，点它只展开菜单；
  真实动作项在 `aria-controls` 指向的 popper 里。
- **处置**：先展开再点菜单项；或直接调端点。**一次这类误报能刷出 4 条假缺陷**。

### 2.3 程序化赋值不触发 Vue 响应

- **症状**：搜索/保存被判「无效」「丢失」，但手工操作正常。
- **根因**：`evaluate` 直接改 `input.value` **不触发 v-model**，接口拿到空值。
- **处置**：必须 `locator.click()` + `locator.type()`。这是**头号自证陷阱**——
  遇到「搜索无效/保存丢失」先自查这一点再报缺陷。

### 2.4 固定列 / 重复渲染导致行错位

- **症状**：按行索引操作，结果改到了别的行。
- **根因**：`.el-table__fixed-right` 与主表重复渲染行；部分列表还有整行 ×N 的幻影重复。
- **处置**：在固定列容器内按行定位；断言前先对照**接口 total**，判断是否踩到渲染层重复。
  **行错位会造出「看着成立」的假缺陷**（曾误报「点取消等于保存」）。

### 2.5 按钮文案含空格 / 文案不稳定

- **症状**：`has-text('确定')` 匹配不到。
- **根因**：Element UI 在两字中文按钮里插空格（「确 定」「保 存」）；多语言站点文案还会切换。
- **处置**：用正则匹配，或取 footer 内最后一个非取消按钮；**点完必须验副作用**。

### 2.6 其他固定坑

- 日期区间控件 `fill()` 写不进 → 点开 picker 面板点 `td.available`。
- `.el-checkbox__original` 不可点 → 点 `.el-checkbox__inner`。
- 左侧导航项文本会污染按文本抓按钮 → 抓按钮前限定在内容区容器内（排除 `.el-menu`/`aside`）。
- 富文本用编辑器 API（如 UEditor 的 `setContent`），不要 `fill()`。

### 2.7 弹窗可见性判定：`querySelector` 会命中隐藏副本

- **症状**：点「新增」后判「没有弹窗 / 按钮无响应」。**一次错误的判定逻辑能同时污染整轮几十页结论**
  （实测：83 页探针的 `dialog=false` 与「空提交校验=0」全部由此产生）。
- **根因**：`.el-dialog__wrapper` 在一页里存在**多个**，`document.querySelector` 返回**文档序第一个**——
  往往是一个关闭态的隐藏 wrapper。弹窗其实已经打开。
- **处置**：
  ```js
  const vis = [...document.querySelectorAll('.el-dialog__wrapper,.el-drawer__wrapper,.el-message-box__wrapper')]
    .filter(w => { const cs = getComputedStyle(w); return cs.display !== 'none' && cs.visibility !== 'hidden'; });
  const box = vis[vis.length - 1];              // 取最后一个可见的
  ```
- **判据**：不要只判「存在」，要取到**弹窗标题 + `.el-form-item__label` 列表**再断言打开；
  `display` 之外再兜一层 `getBoundingClientRect().height > 0`。

### 2.8 「新增/添加」按钮常常是**路由跳转**，不是弹窗

- **症状**：点「新增」没弹窗 ⇒ 误判「按钮无响应 / 功能死路」。曾一次性造出 3 条严重误报。
- **根因**：新增入口有三种形态，弹窗只是其中一种：
  1. 路由跳独立表单页（`/shop-guide/add-guide-goal`、`/purchase/add-account-statement`）
  2. 新标签页打开另一套子系统（如装修端 `?decor_type=seller`）
  3. 真弹窗
- **处置**：判「无响应」前必须**同时比对 `page.url`**，按 `dialog / route / newtab / toast / nothing`
  五态分类；只有 `nothing`（无请求、无提示、URL 不变）才允许写缺陷。

### 2.9 分页当前页的 class 不是 `is-active`

- Element UI 分页当前页是 `.el-pager li.active`。用 `.is-active` 会**永远取不到** ⇒ 误报「翻页无高亮」。
- **处置**：断言前先 dump 一次 className（形如 `['1:number active', '2:number']`）再写选择器。

## 3. 接口层测试（这是最出产能的一层）

**前提认知**：业务后台的**前端有校验、后端往往没有**。所以 UI 点测结构性地看不到这类缺陷。
四轮中 A 轮（接口篡改）单独贡献了 19 条缺陷、其中 5 条致命。

### 3.1 写接口的参数传递方式必须逐接口确认

- **症状**：发 JSON body 报「XX不能为空」，或返回 200 却不生效。
- **根因**：同一系统里**混用** `params`（form-urlencoded/query）与 JSON body，
  **且前端 bundle 里的 `data:A` / `params:A` 字面量不可靠**（实测存在「字面写 data、
  实际只认 form」的接口）。
- **处置**：
  ①两种都发；②**以 GET 复查是否落库为准**；③分不清时用 UI 填表提交一次，录下真实请求体。
- **注意假成功**：只吃 form 的接口收到 JSON 会**返回 200 但静默不落库**——不复查就会误判为「已生效」。

### 3.2 判定「后端零校验」的标准

| 响应 | 含义 | 是否缺陷 |
|---|---|---|
| 2xx + GET 复查确认落库 | 后端接受非法值 | **缺陷** |
| 4xx / 明确业务错误码 | 后端有校验 | 不是缺陷 |
| 500 + 明确业务中文（「面额必须大于0元」） | 后端有校验，只是状态码用错 | 不是缺陷（状态码规范问题单列） |
| 500 +「系统发生异常」 | 后端靠异常兜底，无业务校验 | **缺陷** |
| 500 + 序列化/框架异常原文 | 内部实现泄露 | **缺陷（信息泄露）** |

### 3.3 优先打的字段类型

- **数值**：`-1` / `0` / 超大（`999999999`、`1e9`） / `null` / `"abc"` / 小数
- **枚举**：不存在的取值、非法状态
- **引用**：不存在的 id、别人的 id、`0`、`-1`
- **时间**：起止倒挂、只传一端、非法格式、超远未来
- **集合**：空数组、超长数组、重复元素
- **分页**：`page_size` 超大/负数/字符串；`page_no` 负数

**已知高发结果**：负数被接受并**反向影响库存/金额**；超大值直接落库；不存在的引用被静默存 `null`。

### 3.4 安全类专项

- **越权矩阵**：必须用**受限账号**（不是超管）扫全部读写端点。重点 `export`/`download`。
  已知形态：读接口全通、写接口认证通过直接到业务层、**同一资源 POST 有校验而 DELETE 无**。
- **信息泄露**：类型不符 → 框架异常原文；配置接口明文回显密钥；错误提示含内部包名。
- **注入**：LIKE 通配符（`%`/`_`）未转义 → 返回全表（**这不是 SQL 注入，别升级定性**）。

## 4. 状态机与「非法路径」测试

**这是黑盒测试产出最高的方向**，因为 UI 只暴露合法路径。

### 4.1 通用检查清单

对每类单据过一遍：

- [ ] **非法流转**：终态能否回到中间态（已完成→改回待确认、已作废→复活、已退款→改已发货）
- [ ] **重复操作**：同一操作连发两次是否产生副作用（重复入账、重复退款、重复扣减）
- [ ] **幂等**：同一请求重放是否二次生效
- [ ] **跨模块同步**：状态变了，库存/财务/统计/通知是否跟着变
- [ ] **前置校验**：是否存在「跳过全部流程直达终态」的路径

### 4.2 实测高发形态（换平台时优先验）

- 终态单据再提交 → **二次入账**（可循环刷数据）
- 作废单可被另一端点**复活** → 作废形同虚设
- 草稿单可直接置**终态**，跳过提交/审核/入库
- 数量与金额字段**互相脱钩**（明细 1 件、单据头写 99999999）

**关键**：这些 UI 上都点不出来，必须从接口层构造。**发现它们的前提是先枚举出全部状态类端点**——
从建单页/详情页的前端 bundle 里找 `url: ... , method: ...` 的调用点，比猜路径快得多。

## 5. 跨模块对账（单点测试永远抓不到）

单看每个页面都对，合起来才错——这类缺陷只能靠**对账**。

对账三式，逐模块套用：

1. **同源三出口**：列表 / 导出 / 统计页 = 同一组数？不一致就是缺陷。
2. **合计 = 明细之和**：总览指标 vs 明细逐项求和（财务、库存、业绩都要做）。
3. **公式自洽**：金额/均价/比率是否满足自身定义。
   例：`均价 × 数量 == 总成本`、`Σ(单价×数量) == 合计`、`实付 − 成本 == 利润`。

**实测战果**：财务毛利率算错（虚高 5 倍）就是靠 ② ③ 挖出来的；
库存三套账不一致（库存查询 / 批次Σ剩余 / 流水净额）靠 ① 挖出来。

**注意**：对账前先确认**取的是哪个字段**——用错字段会造出假缺陷
（实测把「售价」字段当「采购价」用，一度误判 23 行金额异常）。

## 6. 数据卫生（接平台第一天就要做）

**系统可能没有清理能力**。实测平台**没有**冲销/作废/反审核/红冲入口，部分单据连 DELETE 都没有
（采购单 405、已开始的活动不可删），造出的脏数据**永久残留**（实测留下 1 亿件假库存 / 159 亿假成本）。

**开工前必须摸清**：

- [ ] 哪些单据**有** DELETE？哪些只能置终态？（从 bundle 找 `method:"delete"`）
- [ ] 有没有冲销/反审核？没有的话**写操作一律不可逆**
- [ ] 有没有回收站/软删除？

**据此下发纪律**：

- 改字段优先「发非法值看是否被拒」，**不要真的写进去**
- 无法复原的操作（删除、状态推进到终态、调拨出库）**只测是否被拒，不真做**
- 必须真做的，先记录原值、改完立刻改回，并在报告里逐笔披露残留
- 测试数据统一加前缀，便于事后识别

**本轮教训**：这些纪律是在**已经造成污染之后**才总结出来的。下次应在派单前就写进任务书。

## 7. 误报复核（产出质量的守门环节）

四轮产生 18 条误报，全部复核留证。**误报不清理会直接毁掉交付物的可信度**。

### 7.1 复核流程

1. **换真实控件重做**：按 §2 的铁律重新取证，不复用原脚本结论
2. **给反证**：能证明「原判据本身有问题」最好（如「点了隐藏按钮」）
3. **分清三类**：
   - **误报** → 撤回，记入复核表并写明依据
   - **描述修正** → 缺陷存在但结论不对（如「清空未生效」实为「清空后不重查」）
   - **确认** → 定稿

### 7.2 必须交叉复核的情形

- **同一现象由两人分别报告** → 结论不一致时必须隔离复测
- **同一 popover 里累加条件** → 极易造成误判：实测「4 个下拉全失效」实为条件未清空所致，
  真实缺陷只有 1 个
- **自家脚本的前序写入干扰后续断言** → 必须逐笔归因到单据号，或每轮重开页面

### 7.3 自我更正要留痕

lead 自己报的缺陷被指出有误时，**更正过程本身要写进报告**（保留原结论 + 更正依据），
便于追溯——这比悄悄改掉更有价值。

## 8. 分层与派单

**有效的分层**（四轮验证）：

| 层 | 范围 | 特点 |
|---|---|---|
| 全站巡检 | 全部页面只读打开 | 快，抓 5xx/白屏/JS 报错 |
| 页面级 | 按模块分工，真点真填 | 抓交互与校验 |
| 场景级 | 跨模块完整业务流 | 抓状态机与一致性 |
| **接口层** | 绕过前端直打后端 | **产出最高**，抓零校验与越权 |
| 补测层 | 针对前几轮的盲区 | 对账/注入/并发/维度排除 |

**派单要点**：

- 每个模块一个负责人，**页面清单要具体到路径**，不要只说「测 X 模块」
- 任务书必须含：环境坑（代理/编码）、工具用法、判据纪律、**数据卫生纪律**
- 要求可计数的自检（覆盖页数 / 交互次数），否则会退化成「只逛不点」
- **发现工具层缺口时立刻广播**（如「写接口用 params 不是 body」），一次广播能救回全队的产出

## 9. 新平台接入检查清单

开工前逐项确认，缺哪项先补哪项：

- [ ] **网络**：是否需要绕代理？不绕会得到「站点打不开」的假结论
- [ ] **登录**：能否自动化？是否需要验证码？**认证头格式**（是否带 `Bearer` 前缀）？
      凭据走环境变量，登录态文件进 `.gitignore`（**绝不入库**）
- [ ] **技术栈**：UI 组件库是什么（查找该族的已知探测坑）？路由类型（hash / history）？
- [ ] **入口**：有几个前端入口（后台/商家端/客户端）？共用 API 域吗？
- [ ] **接口面**：API 前缀有几种？写接口如何发现（建单页录请求 vs bundle 检索）？
      参数传递方式（params / body / 混用）？
- [ ] **数据卫生**：有 DELETE 吗？有冲销吗？（决定写操作纪律）
- [ ] **能力边界**：有没有不存在的功能（如打印）？哪些功能依赖外部系统（如第三方凭证）？
      **先排除，避免整轮白测**
- [ ] **权限**：有受限账号可做越权测试吗？没有就先建一个
- [ ] **可复原性**：哪些操作一旦执行就回不去？（列成清单贴进任务书）

## 11. 登录与验证码（可复用配方）

**登录不是准备工作，是第一个被测对象**。登录跑不通，后面全部产出为零；
而登录「看起来通了」（URL 变了）与「真的通了」（业务接口 200）是两件事。

### 11.1 登录成功的判据

- **不要用 URL 变化 / 出现头像 / 无报错当判据**。判据 = 登录后发一个**业务只读接口**拿到 200 + 预期数据结构。
- 失败要分类：账号错 / 验证码错 / 风控拦截 / 代理不通 / 前端路由变了。**这四类的处置完全不同**，
  混成「登录失败」会让人反复重试同一个根因。
- 登录页本身就是缺陷面：口令是否明文进 query？验证码是否可重放？错误提示是否泄露账号是否存在？
  （实测某系统登录口令以 **MD5 明文放 GET query**，属安全面顺手记录项。）

### 11.2 验证码三档处置（按成本从低到高）

| 形态 | 处置 | 注意 |
|---|---|---|
| 无验证码 | 直接表单提交 | 最省事，优先确认 |
| 固定长度图形码（4 位数字/字母） | **OCR**（如 ddddocr）自动识别 | 识别失败要重试刷新验证码，不重试同一张 |
| 滑块 / 点选 / 语义题 | 人工介入或换测试账号 | 不要硬刚，成本高于收益 |

- **截取验证码元素本身**，不要截整页再猜坐标；整页里往往有多个图形元素。
- OCR 是**确定性离线能力**，比「让模型看图」稳定得多。**多模态读图只在 OCR 不可用时兜底**——
  且前提是所有成员模型都支持读图（实测有模型不支持读图直接失败，见 §14.6）。
- OCR 成功率不是 100%：失败重试要有上限（如 3 次），超限换人工，并把「连续失败」当成环境问题上报而非缺陷。

### 11.3 登录态落盘与多实例共享

- 落盘形态：Playwright `storage_state`（cookie + localStorage），一次登录、N 个会话复用。
- **同一份 state 文件可被多实例并发共享**（11 个并发测试实例实测不互踢），
  这比每成员各自登录省掉 N 倍验证码成本，也避免触发风控。
- **每成员独立 state 文件是反模式**：登录次数 ×N、验证码失败率 ×N、风控概率 ×N，且账号可能被锁。
- state 会过期。**自愈策略**：任一请求收到 401/403 → **重登一次** → 覆盖写 state → 重试原请求一次。
  重登仍失败则终止该成员任务并上报，不要无限重试（会把自己锁在风控里）。
- **state 文件是凭据**：进 `.gitignore`，不进缺陷证据包，不入库，不外发。
  Atlas 侧对应纪律见 `credential_gate.py`（凭据词表与净化刀的唯一实现）与 `runtime.resolve_account/require_account`
  （账号只从 env / 私有 `session.json` 解析，空账号在开浏览器前拒）。

### 11.4 重放鉴权头必须原样带上

接口层测试的第一道坎：**重放请求得到的 403 常常是「头没带对」，不是「越权被拦」**。

- 先抓一次**该会话真实业务请求**的完整头，逐项比对：头名大小写、`Bearer` 前缀有无、
  自定义业务头（如 `uuid` / `apptype` / `isc-app`）、cookie 的域。
- 这些头通常是前端拦截器统一注入的，**在页面上下文里发 fetch 就等于免费带上了**——
  这是最稳的做法（比在外部用 requests 拼头可靠）。
- 反过来：**做越权测试时必须把这些头带上**，否则你测的是「没登录」而不是「没权限」（见 §12）。

### 11.5 代理与浏览器是可复用的环境坐标

- **代理方向是站点属性**，同一套系统的两个入口可能相反（实测：A 端必须直连、B 端必须走代理）。
  写进插件配置，别靠人记。判据：不绕代理时得到「站点打不开」，这与「站点挂了」在报告里长得一样。
- Playwright 自带浏览器缺失时，指向系统浏览器（Atlas 用 `ATLAS_BROWSER_EXECUTABLE`；
  裸脚本用 `executable_path`）。这是**环境**问题，不要报成产品缺陷。

### 11.6 可直接复用的登录骨架

参数全部来自 env，脚本里**不出现任何账号/口令/端口字面量**：

```python
import os
from playwright.sync_api import sync_playwright

USER, PWD = os.environ["SNA_USERNAME"], os.environ["SNA_PASSWORD"]
BASE      = os.environ["SNA_SELLER_URL"].rstrip("/")
STATE     = os.environ.get("SNA_STATE", ".state/seller.json")   # 进 .gitignore
PROXY     = os.environ.get("SNA_SELLER_PROXY", "")               # 空=直连

def login(page, ocr) -> bool:
    """ocr: 接收 PNG bytes，返回识别文本。返回 False 表示重试耗尽。"""
    for _ in range(8):                              # 有上限，不无限重试
        page.goto(BASE + "/login", wait_until="load", timeout=60000)
        page.wait_for_timeout(3500)                 # 等验证码图片渲染
        ins = page.query_selector_all("input.el-input__inner")
        img = page.query_selector("img.verification-code")
        if len(ins) < 3 or img is None:
            continue
        code = ocr(img.screenshot()).strip()        # 只截验证码元素
        if len(code) != 4:                          # 长度不符直接换一张
            continue
        ins[0].fill(USER); ins[1].fill(PWD); ins[2].fill(code)
        page.click("button:has-text('确认登录')")
        page.wait_for_timeout(4500)
        if "/login" not in page.url:                # 弱判据，见 §11.1
            page.context.storage_state(path=STATE)
            return True
    return False
```

复用要点：多实例都读同一份 `STATE`（不互踢）；`goto` 后发现被弹回 `/login` 就调一次 `login`
并把 state 覆写（自愈，见 §11.3）；**state 文件与日志都不进仓库**。

## 12. 权限强制力测试（认证 ≠ 授权）

**这是最容易被前端表现骗过去的一类**：菜单隐藏、按钮消失、URL 直访被重定向，看起来权限体系很完整——
但那只说明**前端**做了权限。要证明权限存在，必须证明**后端**拒绝。

### 12.1 四层判据，缺一层就不能下结论

| 层 | 手段 | 通过 | 不通过 |
|---|---|---|---|
| 菜单可见性 | 受限账号登录后读侧边栏 DOM | 未授权菜单不出现 | 该隐藏的还在 |
| URL 直访 | 直接 `goto` 未授权路由 | 重定向/无权限页 | 页面正常渲染 |
| 按钮收敛 | 进有权限的列表页看操作列 | 未授权操作按钮不渲染/禁用 | 仍可点 |
| **接口重放** | **抓受限会话真实鉴权头，重放未授权端点** | **403/业务无权限码** | **200 + 数据** |

**只有第四层通过，才能说「权限生效」。** 前三层全绿 + 第四层 200 = **权限形同虚设**（实测形态，严重级）。

### 12.2 搭一套权限测试的前置动作

1. 建一个**受限角色**（只勾最小权限，如「库存查询」一项），不要用超管。
2. 绑一个**独立的测试账号**（别改现有账号的角色——会污染别人的测试会话）。
3. **新开一个 context** 登录该账号（不能在同一浏览器里换号，localStorage 会串）。
4. 从这个受限会话里抓一个真实业务请求，记下**完整头**（见 §11.4）。
5. 用这套头逐一重放：先扫读接口，再扫写接口，最后扫 `export`/`download` 类。

### 12.3 扫哪些端点

- 从**受限账号能访问的页面**的 bundle 里抽端点（这些至少不会 404），再补上它无权访问的模块端点。
- 重点扫：列表（是否返回全量）、详情（是否能用 id 猜）、写操作（能否越权改）、**导出（最常漏）**。
- 判据分类：
  - `403` / 明确业务无权限码 → **后端有授权，通过**。
  - `200` + 业务数据 → **缺陷（严重）**。证据要带：受限账号 ID / 角色 / 被访问端点 / 响应数据条数与字段名。
  - 无 token 时 403 但受限 token 200 → **认证有效、授权缺失**，这两句必须分开写，不要合并成「鉴权有效」。

### 12.4 实测高发形态（换平台优先验）

- 前端三层全生效（菜单隐藏 / URL 重定向 / 按钮收敛），**后端零校验**——受限店员重放自己的 JWT
  就能拉到商品、订单、角色全量数据。
- JWT payload 里的 `roles` 只是**声明**，服务端不校验声明内容。
- 同一资源 **POST 有校验而 DELETE 无**（写操作内部也不一致，逐个方法验，别测一个推全部）。
- 读接口全通、写接口认证通过直接到业务层（缺的是授权，不是认证）。

### 12.5 必须写进报告的盲区

- 只测了「一个受限角色」，多角色叠加/继承的权限没测。
- 导出类端点未全扫（导出常走另一套权限判断）。
- 没有第二个真实账号可做 IDOR 交叉验证（拿 A 的 id 用 B 的 token 访问）。
- 「403」也分「后端拦的」与「网关/WAF 拦的」，未区分时如实标注。

## 13. 详情页直链与刷新可达性

**症状**：从列表点进详情一切正常；用户把 URL 收藏、刷新、或从消息里点开 → 被弹回首页。

- **根因**：列表点入时靠内存里的列表行数据渲染，详情页不自己拉数据；
  刷新后 store 空了，路由守卫判定「无上下文」就重定向。
- **判据**：列表点入 **≠** 页面可用。必须单独验两次：① F5 刷新 ② 把 URL 复制到新标签页直开。
  对照组用「新建表单页」——同类路由若正常，说明问题是详情类路由特有，不是全局路由配置错。
- **脚本化全站审计**：遍历列表页 → 点第一行进详情 → 记 URL → `new_page.goto(该URL)` →
  比对最终 URL 是否等于原 URL。**脚本能一次扫完几十个详情页**，比人点快一个量级。
- 实测：83 页审计后只有详情类路由中招（`/order/detail/<id>`、`/order/service-detail/<id>`），
  列表页、新建页、编辑页都正常——**这种「只有一类路由坏」的分布本身就是根因线索**，写进报告。

## 14. 委派编排与质量闸门

黑盒测试的产出质量不取决于人数，取决于**闸门**。实测：散文式任务书 + 页面清单 = 成员「只逛不点」；
加可计数闸门后才产出有效缺陷。

### 14.1 任务书必须含可计数动作

每个成员的报告里强制带：

- `visitedPages`：真实打开过的路径列表（不是「计划测的」）。
- `interactions`：每个页面的**交互次数**（点击 / 填表 / 提交 / 切换），不是「打开次数」。
- `emptyPages`：进去后**没有任何可交互元素**的页面清单（这些要么是空态，要么是缺陷，必须逐页判定）。
- `bugs[]` / `scenarios[]`：结构化 JSON，字段固定（见 §10 的字段表）。

**没有计数的报告按未完成处理**。这一条比任何措辞都有效。

### 14.2 lead 先跑黄金样本

派单前 lead 自己跑通 1 个模块，产出**一条格式完整、证据齐全的缺陷**（含请求实参 + 响应片断 + 判定依据），
连同「怎么跑」一起发给成员当模板。成员会照抄格式——**给散文他们写散文，给样本他们填样本**。

### 14.3 任务书必须附三张清单

1. **已知基线**：上一轮已经测过的页面 / 已知问题（避免重复报同一批）。
2. **误报清单**：已经证伪的探针姿势（如「分页无高亮」实为选择器错），写明**为什么是假的**。
3. **工具坑**：该站点特有的交互铁律（弹窗副本 / 搜索按 Enter / 路由跳转非弹窗 / 详情页路由）。
   一次广播能救回全队产出（实测「写接口用 params 不是 body」这条广播救回整轮接口测试）。

### 14.4 唤醒与去重

- 成员被中断后恢复，第一句话必须写「**不要重做已完成部分**」+ 已完成清单（页面 / 场景编号）。
- 同一现象被两人分别报时，先隔离复测（见 §7.2），不要直接合并或丢弃。
- 成员重复报「已知基线」里的问题时，驳回并指出基线条目编号，不要静默删除。

### 14.5 模型出口故障的处置次序

1. **先测网关本身**（一个最小请求），确认是出口挂了还是模型挂了。
2. 网关正常而个别模型不可用 → **换模型**，不要等。
3. 换模型后必须重测一个最小任务（能登录 + 能读一页），**再**恢复派单。
4. 故障期间**不要让成员反复重试**——重试不解决出口问题，只会把失败次数刷进统计。

### 14.6 派单纪律：不要要求看截图

- 有模型不支持读图，任务书里要求「看截图判断」会直接导致该成员失败。
- **证据一律走「接口 URL + 响应片断 + JS 取值」**，截图只作为辅助留档，不作为判据。
- 这条同时提高可复核性：截图无法 grep，响应片断可以。

### 14.7 产出必须机器可校验

- 每个成员交固定 schema 的 JSON（不是 markdown 散文），lead 用脚本合并、去重、统计。
- 缺字段 / 类型不对的条目直接退回，不要人工补全——**人工补全会把成员的判断混进 lead 的判断**，
  事后无法归因是谁的结论。

## 15. 破坏性按钮：点下去之前先验证

§6 说的是「不可逆操作只测是否被拒」。**这一节补的是更前置的一步：你连它是不是不可逆都不知道。**

### 15.1 默认假设：删除按钮可能没有二次确认

- 实测事故：点「消息管理 → 全部删除」，**无任何确认框**，直接删除 10 条真实消息（未读数 96→86）。
  探针脚本只点了一下，损伤是既成的。
- 所以纪律是：**「删除 / 清空 / 批量删除 / 作废」类按钮，第一次点击必须发生在自建数据上**。
  没有自建数据时，**不点**——把「无确认框」这个结论本身作为缺陷报（这不需要真的删数据就能证明：
  从按钮到发出 DELETE 请求之间的链路里没有 confirm 层，抓包即可）。

### 15.2 安全的验证姿势（按代价从低到高）

1. **读 bundle**：找该按钮绑定的 handler 是否调用 `confirm` / `$confirm` / 二次密码框。静态可证。
2. **建 1 条自建数据**（统一前缀，如 `autotest_msg_001`），对它点删除，观察：
   ① 有无确认框 ② 发出什么请求 ③ 列表是否真实减少。
3. **只测「是否被拒」**：构造越权/非法参数的删除请求，看后端是否拒绝——**不发真实的成功删除**。
4. 必须真删时：记录删除前后条数、逐笔记录被删对象标识、**在报告里披露残留影响**。

### 15.3 事故申报

- 一旦造成真实数据副作用：**立即停止该类操作**、如实记录（时间 / 操作 / 影响条数 / 前后快照）、
  在最终交付里单列「测试副作用披露」一页。
- **不要试图悄悄恢复或抹平**——恢复动作本身可能造成二次污染，且抹平会让报告失真。
- 这条同时是缺陷证据：**无确认框的删除按钮本身就是严重缺陷**，事故是它的实证。

## 16. 通用知识包与平台包的分工

换平台时**不需要从零总结判据**：机制性判据（组件铁律、接口篡改方法、状态机/对账方法、
越权测试方法等）已抽进**通用知识包**；平台特有的坐标（真实路径、自定义 class、token 键、
env 名、业务字段）留在平台包。本文 §1–§15 讲的是「流程与判据纪律」，通用知识包讲的是
「可直接复用的判据条目」。

### 16.1 三层位置：通用判据放哪、平台特有放哪

| 层 | 路径 | 放什么 | 谁维护 |
|---|---|---|---|
| 私有目录 | `ATLAS_KNOWLEDGE_DIR`（仓库外） | 真实账号/代理/真实页面路径、人审批准成果 | 项目组私有，**不入库** |
| **通用包** | `src/atlas/plugins/_common/knowledge/` | **脱离平台坐标可直接复用的机制判据** | 引擎层维护（业务中立、跨插件共享） |
| 平台包 | `src/atlas/plugins/<业务>/knowledge/`（如 `snalai`） | 平台坐标与业务事实：真实路由、自定义 class、token 键、env 名、业务字段、平台具体缺陷 | 平台插件维护者 |

通用包三个文件（顶层均为 `policy` + 同名键，与平台包同名文件结构一致——消费方按
`.get("components")` / `.get("pitfalls")` / `.get("checklist")` 读，无需区分来源）：

| 文件 | 内容 | 判据 |
|---|---|---|
| `components.json` | 15 条组件铁律（弹层多副本、触发器≠动作按钮、固定列重复渲染、分页 `li.active`…） | selector 只用 `.el-*` 等**通用 CSS**；平台自定义 class（非 `.el-*` 形态）不进通用包 |
| `pitfalls.json` | 47 条机制坑点（症状→根因→处置） | `scope` 只用**机制标签**（`element-ui`/`vue2`/`api`/`state-machine`/`authz`/`export`/`delegation`/`data-hygiene`/`cleanup` 等，词表见台账 §5），不含平台名；`status` 一律 `pending_review` |
| `domains.json` | 新平台接入检查清单 `checklist` | 六类通用检查项：`network_and_proxy` / `login_and_captcha` / `api_surface_and_params` / `data_hygiene` / `capability_boundaries` / `restorability` |

### 16.2 什么算「通用」（提炼判据）

一条知识进通用包必须能回答：**脱离平台坐标后能否直接复用？** 三种处置：

- **通用**：整条是机制判据/方法 → 抽入通用包（剥掉示例里的平台坐标）。
- **拆分**：一条里混着通用方法与平台事实 → 方法抽入通用包，平台部分留平台包。
- **平台特有**：内容是平台事实/业务坐标/具体缺陷 → 留平台包。

无法判定是否通用的一律**留平台包**并写明理由——不写「看起来对」的猜测。

**分类台账**：`docs/element-ui-generic-knowledge.md`——逐条记录每个原始条目的判定与去向
（§1/§2 逐条表、§3 数量小结、§4 无法判定/有意取舍、§5 scope 机制标签词表）。**接入新平台
或提炼新通用条之前先查台账**，避免重复造判据；新平台上新发现的机制坑点按同口径回流通用包，
并更新台账逐条去向。

### 16.3 新平台接入顺序

按依赖走，不要跳：

1. **跑通登录（§11）** → 产出可复用的 storage state；
2. **摸清代理方向（§11.5）** → 写进插件的 `network`（代理方向是站点属性，别靠人记）；
3. **枚举页面与接口面（§8/§3）** → 写进平台包 `domains.json`；
4. **通用包已自带机制判据**：组件铁律与机制坑点**直接可用，不必重写**——§2 的探测坑、
   §3 的接口篡改方法、§4 的状态机检查、§5 的对账三式、§12 的越权四层判据都有对应条目；
5. **只补平台坐标**：真实路径、自定义 class、token/localStorage 键名、env 名、业务字段名。

顺序的理由：1–3 产出平台坐标（私有 → 平台包），4 复用通用判据（零成本），5 收尾补坐标。
**没有 1–3 的产出，后面全是无效点击。**

### 16.4 用 plugin_api 通用根把通用包接进新插件

引擎提供通用根 helper（`src/atlas/plugin_api.py`）——**路径单一来源**，插件不得自己拼：

```python
from atlas.plugin_api import common_knowledge_root

KnowledgeBase(root=私有目录,
              fallback_root=平台包内知识,
              base_roots=[common_knowledge_root()])
```

加载语义分两层，别混：

- **影子层 `fallback_root`**：`load()` 逐文件取根序列里**第一个存在的**根，同名文件**整份胜出**
  （影子遮蔽）。单 `Path` 传参 = 存量两级行为逐字不变。
- **组合层 `base_roots`**：`load_composed(name)` 在 `load()` 影子结果上**并入**通用包——顶层 dict
  按 key、pitfalls 行按 `id` 去重（无 id 按内容摘要去重）、components 按组件名合并，**靠前者赢**；
  `base_roots=None/空` 时与 `load()` 逐字等价（零行为变化）。

为什么必须用组合层而不是影子层：平台插件（如 `snalai`）自带 `pitfalls.json`，影子语义会让通用包
**整份不可见**——组合层按条目并入，平台专有条目胜出、通用条目补齐缺口。

可见性：`pitfalls(domain)` 走 `load_composed`，判据 = **`domain in scope` 或 `"generic" in scope`**。
通用包每行 `scope` 带数据层打的 `generic` 标记 → 对任意平台域可见；平台专有行 `scope` 只有
平台名+机制标签、不带 `generic` → 对别的域不可见（不误配）。

- 写路径永远只落 `root`（私有目录，`ATLAS_KNOWLEDGE_DIR`）；影子层与组合层一律**只读**
  （红线 #135：包内资产只读，批准写回只落私有目录）。
